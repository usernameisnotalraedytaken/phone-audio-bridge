# 到达抖动与漂移：能测什么、怎么测、测到多少

**日期**：2026-10-17
**相关代码**：`SnadArrivalStats.cs`（纯计算）、`SnadReceiver.TrackArrival`（采集）、
`SnadArrivalStatsTest.cs`（确定性验证）、`SnadSender.cs`（故障注入）

---

## 一、协议里一直有发送端时间戳

`SnadProtocol.kt` 的包头在偏移 14 处写着 `timestampMs`（手机侧单调时钟低 32 位），
手机一直在发。但**接收器从来没读过它**——这个字段此前是纯冗余。

现在用上了。它带来两个真正有用的量：

| 能得到 | 用途 |
|---|---|
| **抖动**（单程延迟的波动） | 直接回答"抖动缓冲该留多深" |
| **漂移**（两端时钟速率差） | 验证漂移补偿是否在工作，并给出实际速率 |

## 二、为什么算不出绝对延迟

发送端时间戳来自手机的单调时钟，接收端用本机 `Stopwatch`，两者**起点与速率都不同**。
没有往返测量（RTT）就无法确定这个偏移。

所以代码里诚实地只算**差值的统计量**：

```
offset_i = (本地到达时刻_i − 本地首包时刻) − (发送时间戳_i − 首包时间戳)
```

`offset` 里含一个未知常数（时钟偏移）。**常数不影响变化**，因此
抖动（相邻 offset 的差）与漂移（offset 的长期趋势）都可以精确得出。
绝对延迟另用声卡回环测，那条路不依赖手机时钟。

## 三、确定性验证（`SnadArrivalStatsTest.exe`）

把计算抽成纯函数 `ArrivalStats.Compute` 后，可以用合成序列断言，
期望值全部可解析算出：

| 输入 | 期望 | 实测 |
|---|---|---|
| 常数序列（含 3.5ms 时钟偏移） | 抖动 0、极差 0、漂移 0 | 0.0000 / 0.0000 / 0.0000 |
| 均匀抖动 U(0,6) | J/3 = 2.00 ms | **2.00** |
| 均匀抖动 U(0,12) | J/3 = 4.00 ms | **4.00** |
| 均匀抖动 U(0,30) | J/3 = 10.00 ms | **9.99** |
| 线性漂移 +5 ms/分 | +5.00 | **+5.00** |
| 线性漂移 −12 ms/分 | −12.00 | **−12.00** |
| 单点尖峰 40ms | 极差≈40，抖动不被放大 | 极差 40.0、抖动 0.485 |
| 样本 31 个 | 返回 false，输出全 0 | 符合 |

### 验证时发现并修掉的两个真 bug

1. **漂移恒为真值的 75%**
   分母用了整个窗口时长，而首尾两段的均值分别位于各自段中心，
   相隔只有 3/4 窗口。注入 +5 读到 3.75、注入 −12 读到 −9.0，
   比值恒为 0.75——这个特征直接指向分母选错。
   改为**取段内平均时刻之差**作分母，不再假设段长与位置。

2. **漂移被 32 位时钟回绕污染**
   原先用 `Environment.TickCount`（32 位，约 49.7 天回绕），
   回绕时"本地经过时间"跳成负数，一次跳变就把漂移污染成几十上百 ms/分。
   改用 `Stopwatch`（64 位单调）。
   注意 `Environment.TickCount64` 是 .NET Core API，本项目（Framework 4.x）不可用。

## 四、端到端注入的局限（重要）

`SnadSender` 能注入传输抖动，但**不能用它做数值校验**：

- `Thread.Sleep` 的粒度约 15.6ms，`sleep(0..12ms)` 实际只会落在 {0, ~15.6} 两档，
  注入分布不是真正的均匀分布；实测注入 0..30ms 时极差已达 44.9ms。
- 加上发包器自身的调度误差与接收端可能的欠载，噪声与被测量同量级。

它的正确用途是**定性检查**——"统计有没有响应"。实测三级注入：

| 注入传输延迟 | 抖动读数 | 极差 | 漂移 |
|---|---|---|---|
| 0（仅本机回环） | **0.36 ms** | 1.0 ms | −1.2 ms/分 |
| 0..12 ms | 1.73 ms | 16.9 ms | +11.1 ms/分 |
| 0..30 ms | 8.69 ms | 44.9 ms | +13.0 ms/分 |

单调上升，说明采集链路（读时间戳 → 计算 offset → 统计）是通的。
精确性由上面的合成序列断言保证。

### 顺带得到的一个有用数字

**本机回环的抖动是 0.36 ms、极差 1.0 ms。**
这回答了"在没有网络的情况下缓冲需要多深"：约 1~2 ms 足够。
真实 WiFi 会显著高于此，而那正是这几个统计量存在的意义——
让"缓冲该留多深"从猜测变成读数。
