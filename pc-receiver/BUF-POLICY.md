# 缓冲策略：static / adaptive / calibrated

**日期**：2026-10-17
**代码**：`SnadBufferPolicy.cs`（三种策略）、`SnadReceiver.cs`（接线）、
`SnadBufferPolicyTest.cs`（确定性验证）
**为什么现在做**：回环实测证明声卡缓冲池不是稳态延迟（见 `LATENCY-MEASURED.md`），
真正决定延迟的是环形缓冲停在多深——所以这个深度该被策略化。

---

## 一、三种策略

| 模式 | 目标水位怎么定 | 适用 |
|---|---|---|
| `static` | 固定 `TargetBufferMs` | 行为可预测，v2.0 的行为就是它（默认） |
| `adaptive` | 按实测持续调整，受 min/max 约束，速率可配 | 网络状况会变 |
| `calibrated` | 启动时观察一段，锁定后不再变 | 环境固定，要可复现 |

共同的关键量是**掉坑深度** = 目标水位 − 读取时的实际可用量。
它等于"目标再低这么多就会欠载"的量，因此"下限 + 安全系数 × 掉坑"就是够用的深度。

- `adaptive`：期望值 = `min + 2 × (掉坑EMA + 欠载惩罚)`，每次按 `adaptRate` 移动一小步。
- `calibrated`：标定期内保持配置值，结束后锁到 `min + 1.5 × 95分位掉坑`。

## 二、为什么不只用"水位观测"

水位只在**读取那一瞬间**采样，看不到"块内被读空"。
实测：40 ms 抖动下 `adaptive` 已经欠载 8 次，却仍在把目标往低处压——
因为它根本没看见失败。因此加了第二条反馈：环形缓冲每报一次欠载就通知策略，
`adaptive` 立即抬高期望值并缓慢衰减，`calibrated` 把这次欠载记为"整段掉光"的样本。

## 三、确定性验证（`SnadBufferPolicyTest.exe`）

合成序列喂 `Observe`，期望值可解析算出：

| 场景 | 期望 | 实测 |
|---|---|---|
| static，掉坑 30 ms × 500 次 | 恒 80 | **80** |
| adaptive，可用量恒等于目标 | 收敛到下限 40 | **41** |
| adaptive，每次掉 30 ms | 40 + 2×30 = 100 | **100** |
| adaptive，持续空 | 顶到上限 120 | **120** |
| calibrated，掉坑 20 ms | 40 + 1.5×20 = 70 | **70** |
| calibrated，锁定后再观测 | 不再变化 | **70** |
| calibrated，无掉坑 | 锁到下限 40 | **40** |
| 工厂，`buffermode=乱写` | 退回 static 并 WARN | **StaticPolicy** |

## 四、端到端对照（同一接收器，发包器注入抖动，各 32 秒）

### 抖动 0..15 ms

| 策略 | 目标 | 实测水位 | 欠载 |
|---|---|---|---|
| static | 80 ms | 72 ms | 3 |
| adaptive | 44 ms | 49 ms | 2 |
| calibrated | 75 ms | 83 ms | 3 |

### 抖动 0..40 ms

| 策略 | 目标 | 实测水位 | 欠载 |
|---|---|---|---|
| static | 80 ms | 87–113 ms | 5 |
| adaptive | 43–51 ms | 38–52 ms | 8 |
| calibrated | 88–90 ms | 75–78 ms | 4 |

**读法**：延迟差距明确（adaptive 约为 static 的一半），
欠载次数差距在 4–8 次/32 秒这个量级、且含起播瞬态，差别不足以据此判定优劣。
所以 `adaptive` 的实际含义是"用少量偶发欠载换一半的缓冲延迟"，
而不是"又低延迟又更稳"——后者没有测到。

## 五、过程中修掉的两个真缺陷

1. **标定值比固定值更差**
   最初锁到 160 ms（static 只有 80）。原因是把**启动瞬间**的掉坑按最大值放大 1.5 倍。
   起播时环刚由预填充建立、调度也最乱，那一下不代表网络常态。
   改为：丢掉前 1.5 s，取稳态样本的 **95 分位**（而非最大值）——
   一次开机、一次系统更新都会造出极大的瞬时掉坑，用最大值定标会让之后永远背着多余延迟。
   修后锁定 75–90 ms。

2. **自适应对欠载完全无感**
   见第二节。

## 六、顺带修掉的发包器缺陷（它曾让一组测量作废）

抖动最初是"在当前时刻加 `sleep(j)`"。抖动一大，发送被不断往后推，
**平均吞吐塌掉**：40 ms 抖动时从 1534 掉到 1115 kbps，接收端被饿死。
那一组三档数据看起来"全都崩了"，其实测的是源跟不上实时，不是网络。

改为：采集与发送分成两个线程，包按"采集 + 基础延迟 + 独立抖动"释放。
基础延迟（默认 80 ms）给抖动留出摆动空间，平均到达间隔仍等于采集间隔。
修后 40 ms 抖动下仍是 476 包 / 9996 ms 音频 / 10.07 秒，吞吐无损。

**教训**：故障注入工具本身必须先被验证不改变它不该改变的量。
否则测出来的"性能下降"可能是仪器的问题。

## 七、复现

```powershell
cd pc-receiver

# 确定性验证（不需要网络与声卡）
.\SnadBufferPolicyTest.exe

# 端到端：接收器用某个档位，发包器注入抖动
.\SnadReceiver.exe --profile balanced
.\SnadSender.exe 127.0.0.1 时长 32 块 21 抖动 40
# 接收器周期日志里会出现 [缓冲策略] 行与 欠载= 计数
```
