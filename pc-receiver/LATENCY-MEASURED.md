# 输出后端延迟实测

**测量日期**：2026-10-17
**机器**：Realtek 板载声卡（设备序号 5）+ Voicemeeter 虚拟设备
**采样率**：48000 Hz，2 声道

本文所有数字都是**实测**，不是按配置算出来的。测量工具：
`SnadWaveOutTest.exe`（waveOut）与 `SnadWasapiTest.exe`（WASAPI）。

---

## 结论

| 后端 | 配置 | 声卡侧在飞 | 欠载 |
|---|---|---|---|
| **waveOut** | 16ms × 16 个（**当前 v2.0 配置**） | **256.00 ms** | 0 |
| waveOut | 16ms × 4 个 | 63.91 ms | 0 |
| waveOut | 16ms × 2 个 | 32.00 ms | 0 |
| waveOut | 8ms × 3 个 | 23.92 ms | 0 |
| waveOut | 4ms × 4 个 | 16.00 ms | 0 |
| **WASAPI 共享** | 缓冲 20ms | **10.33 ms** | 0 |
| WASAPI 独占 pcm24 | 周期自适应，缓冲 3ms | 13.17 ms | 0 |
| WASAPI 独占 pcm24 | 周期 3ms，缓冲 6ms | 15.93 ms | 0 |

### 核心发现

**1. 当前配置的 256ms 里有 240ms 是白付的。**
waveOut 的池子会稳定爬到**最满**且从不饿死——无论池子多深，
它都会填满。也就是说"16 个缓冲"不是一个必要的安全余量，
而是一个**不会被动用的余量**：实测 2 个缓冲也零欠载。
这意味着只靠调小 block 与池深度，就能从 256ms 降到 16ms。

**2. WASAPI 的优势是约 40%，不是数量级。**
实测 10.33ms（共享）对比 waveOut 最好的 16.00ms。
先前"缩小到 1/16"的说法是错的——那是拿 waveOut 的**配置容量**（256ms）
去比 WASAPI 的**实测值**（16ms），口径不一致。
同为实测值，差距是 1.6 倍。

**3. 独占模式并不比共享更快（本机）。**
独占 13.17~15.93ms，共享 10.33ms。独占的价值在于
**绕开系统混音器**（不被系统做音量/增强处理），不在于更低延迟。
这与"独占一定更快"的常见说法不同，但数据如此。

## 踩到的坑（都已修，记录以免重犯）

| 现象 | 原因 |
|---|---|
| `SetEventHandle` 返回 `0x88890001 NOT_INITIALIZED` | 必须在 `Initialize` **之后**调用 |
| 独占模式一律 `0x88890013` / `0x88890016` | 独占模式**不接受 `EVENTCALLBACK` 标志**，去掉即成功；改用轮询 |
| 探测第二个组合就 `0x8889000A DEVICE_IN_USE` | 未显式 `ReleaseComObject`，设备被上一个客户端占住 |
| `GetMixFormat` 的位深读错 | 必须按 `WAVEFORMATEXTENSIBLE` 整体读取才能拿到 `SubFormat`；只读基础结构会靠位深猜，而 32bit 容器既可能是 float 也可能是整数 |
| waveOut 测试量到"96% 池空" | 测试没有重新提交缓冲，池子一次性排空；真实行为是循环提交 |

## 接收器接入后的端到端实测

以上是后端本身的测量。接进接收器后（发包器 → 接收器 → WASAPI 独占 → 物理声卡）
又测了一轮，35 秒连续：

```
累计写入 1446400 帧，渲染 1442453 帧，差额 3947 帧（82 ms = 队列容量）
读=48003  写=48003          ← 读写速率匹配，无持续漂移
丢弃[短0 magic0 版本0 负载0]  ← 零丢包
序列缺口=0（缺 0 包）
队列见底 0 次，欠载 0 次
```

### 一个反直觉的结论：内部环形缓冲的容量**就是**该后端的稳态延迟

写入侧永远有数据（网络持续到达），因此 sink 的内部环形缓冲会
**稳定停在满的状态**。而"停在满"意味着每帧音频都要等整个容量的时间
才轮到播放——所以它不是"越大越安全"，而是**多大就加多少延迟**。

设备自身的缓冲（独占 42.7ms / 共享约 10ms）已经提供了抗调度抖动的余量，
环形缓冲只需覆盖"渲染线程两次取数之间"写入侧的突发。

因此从 150ms 改为 `max(40ms, 2×设备缓冲)`：实测 150ms → **82ms**，
且仍然零欠载。这是本项目里第二个"把余量当安全、实际全是白付延迟"的例子
（第一个是 waveOut 的 256ms 缓冲池）。

### 排查中发现的自身错误（值得记下）

1. **把累计值当增量**：写入重试循环里 `off` 表示"本次已累计写入"，
   在循环内对它求和会把同一批数据加 N 遍（N = 重试次数）。
   由此算出虚高一倍的"接受帧率"，把正常的写入侧误报成"供过于求"，
   白费数轮排查。要累加的是每次实际写入的增量。
2. **用累计值配窗口分母**：诊断里的"每秒速率"必须用窗口内增量计算，
   否则短窗口配长累计必然虚高。

两个错误都表现为"数据自相矛盾"，而真正确认无异常的依据是
**累计写入帧 − 累计渲染帧 ≈ 队列容量**这个恒等式。

## 回环实测（计划 §3.2）

以上都还是"后端内部"的量。计划要求用 WASAPI loopback 录下**实际从设备放出来的声音**，
与"交出去的样本"对齐，得出真实延迟。工具：`SnadLoopback.exe`。

方法：采集该设备的 loopback，按实时节奏（可先灌入预填充）送出唯一特征的噪声串，
在采集波形里定位它，延迟 = (检出位置 − 交出位置 − 静音前缀) / 采样率。

### 结果（同一声卡，48000 Hz，每项 2–3 次取中位）

| 配置 | 实测输出链路延迟 |
|---|---|
| waveOut 16ms × **16**（v2.0 现配置） | **28.67 ms** |
| waveOut 16ms × **4**（池缩小 4 倍） | **31.67 ms** |
| waveOut 21ms × **32**（同 highquality，池放大 8 倍） | **25.67 ms** |
| WASAPI 共享 16ms | **43.67 ms** |

### ~~关键结论：缓冲池深度不是稳态延迟~~ ← **这条结论是错的，已作废**

本节原先写着"池深从 4 改到 32、延迟都在 25–32 ms 不动，所以池不是延迟"。
**那是测法造成的假象**，后续的端到端测量把它推翻了：

- 直连测法里，信号按实时喂给 sink，**池来不及预填充**，
  所以只量到"一块 + 设备"的量级。
- 真实接收器的环形缓冲里一直有数据，`waveOut.Play` 会把整个池填满并保持，
  于是池深**线性**进入延迟。

端到端实测（见下一节）直接给出对照：

| 配置 | 端到端 |
|---|---|
| waveOut 块 16 ms × 池 16 | 317.81 ms |
| waveOut 块 16 ms × 池 4 | 148.50 ms |

差 169 ms ≈ 12 块 × 16 ms。**池深就是延迟**，计划 §12 原本的判断是对的。

保留这一段是为了记住教训：**测量装置的假设会伪装成被测对象的性质**。
"按实时喂入"这个前提在直连测试里是必要的（不控速就测不到稳态），
但它同时消掉了池的预填充——两个要求互相冲突，
唯一可靠的办法是走真实链路（接收器 → 环形缓冲 → 输出）再录回。

### 这个测量包含什么、不包含什么

- **包含**：输出缓冲（至多一块）+ 设备缓冲 + 系统混音 + **采集侧自身缓冲**
- **不包含**：抖动缓冲/环形缓冲的水位（那是接收器内部，另有计数器）
- **不包含**：DAC 之后到实际出声（需麦克风回环）

## 端到端实测（计划 §3.2 要求的那一种）

上面那些是"输出段"。计划要求覆盖**抖动缓冲 + 播放池 + 声卡**，
因此 `SnadLoopback` 增加了 `e2e` 模式：起一个真实的接收器进程，
按协议送流，同时用 loopback 录回，测的是
「包进入接收器」到「出现在声卡输出」的整段。

先按实时喂 3 秒让环形缓冲进入稳态，再送一段噪声串，
记录交出该包时采集端已采到第几帧，回来在波形里找它。

| 档位 / 配置 | 目标水位 | 块 × 池 | **端到端实测** |
|---|---|---|---|
| lowlatency | 60 ms | 16 × 16 | **322.71 ms** |
| balanced | 80 ms | 16 × 16 | **339.81 ms** |
| highquality | 250 ms | 21 × 32 | **814.21 ms** |
| （对照）balanced 但池改 4 | 80 ms | 16 × 4 | **143.08 ms** |
| WASAPI 共享 | 80 ms | 无池 | **210.90 ms** |

每组 4 次、预热 6 秒、中位数。预热从 3 秒延长到 6 秒后分散度明显收窄
（WASAPI 19 ms、waveOut 35 ms），此前的短预热会让环还没到目标水位就开始测。

读法：
- **换后端省 38%**：waveOut balanced 339.81 → WASAPI 共享 210.90 ms。
- **缩池省 58%**：同档位池 16→4，339.81 → 143.08 ms。
- **池比后端更有效**：waveOut 池=4 的 143.08 ms 甚至低于 WASAPI 的 210.90 ms。
  原因是 WASAPI 那 210.90 ms 里仍有 80 ms 的环形缓冲水位，
  而 waveOut 这条路可以把池压到 4 而环水位不变。
- lowlatency 与 balanced 几乎相同（322.71 vs 339.81）：两者池都是 16×16，
  **只调目标水位不动池，等于没调**。

### 矩阵：后端 × 块长 × 池深 × 周期（计划 §10 要求的数字表）

同一套端到端方法，每组 3 次取中位数，预热 6 秒，其余参数固定（目标 80 ms）。

| 后端 | 块长 | 池 / 周期 | **端到端实测** |
|---|---|---|---|
| waveOut | 16 ms | 池 4 | **136.69 ms** |
| waveOut | 16 ms | 池 8 | **204.77 ms** |
| waveOut | 16 ms | 池 16 | **328.65 ms** |
| waveOut | 8 ms | 池 8 | **340.79 ms** |
| waveOut | 21 ms | 池 32 | **734.29 ms** |
| WASAPI 共享 | 16 ms | 周期 3 ms | **195.73 ms** |
| WASAPI 共享 | 16 ms | 周期 10 ms | **210.75 ms** |
| WASAPI 独占 | — | — | **不可测**（见下） |

**池深线性**：4→8→16 每加 4 个缓冲，延迟增加约 64 ms，
与 `池 × 块长` 完全对应。这条关系是本轮最可靠的结论。

**周期有效但幅度小**：WASAPI 周期 3→10 ms，延迟增加 15 ms。

**一处未解释的异常**：块 8 × 池 8（池量 64 ms）比块 16 × 池 4（同为 64 ms）
高出 204 ms。两者在线性模型里应当相同。
一个可能的解释是 waveOut 的时间粒度约 10 ms，8 ms 的块会被向上取整，
于是 8 个缓冲实际占用远超 64 ms——但这一条**尚未验证**，
所以只记录现象，不拿它做设计建议。

**独占模式为什么不可测**：WASAPI 独占绕过系统混音器，回环采集抓不到。
要测只能用物理回环（线路输出接线路输入），本机没有这种接线。
因此独占模式只提供"能不能开"的结论（能力探测会说），不提供延迟数字。

**格式（pcm16 / pcm24 / float32）不进这张表**：它改变的是数据路径精度，
不改变时序。逐样本的正确性由 `SnadBitPathTest` 单独证明
（见 `BUF-POLICY.md` 与 §8④ 的记录）。

### WASAPI 曾经测出 81.67 ms，那是坏链路上的假数

中间出现过一次 81.67 ms，同时伴随读速率 36701/s、丢最旧帧 4128、欠载 2032。
低延迟是"漏掉数据"换来的。追下去发现三个叠加的缺陷：

**缺陷一：pull 补静音**
`pull` 在缓冲不足一块时返回静音，把"没数据"伪装成"有数据"。
调用方照常写进 sink，抖动缓冲被读空却看不出来。
改为"不足一块就返回 null"后：读速率 36701 → 49367/s，欠载与丢帧归零。

**缺陷二：sink 队列容不下上游水位**
队列容量 44 ms 而上游目标是 80 ms，链路变成"刚好够"：
上游一填满就被抽干，设备大半时间放静音。
改为按上游目标水位设定容量后，读速率 29918 → 49825/s。

**缺陷三（最严重）：输入格式与设备格式混用**
接收器的 `pull` 交出的是 **PCM16**，而共享模式下 sink 的设备格式是 **float32**。
`Write` 一律按设备格式解码，等于把两字节样本当四字节浮点读——
设备收到的是稀疏的满幅垃圾。

这个缺陷靠"数字对不上"是发现不了的（计数器全都正常），
是靠**直接监听设备输出**才暴露的：

| 场景 | 峰值 | ≥0.01 样本占比 |
|---|---|---|
| 接收器播放（修前） | 0.99999 | **2.93 %** |
| 什么都不播（对照） | 0.00000 | 0.00 % |
| 接收器播放（修后） | 0.60499 | **98.49 %** |

修法：`Write` 增加 `inputFormat` 参数，输入按声明的格式解码，
中间表示统一为 float，输出再按设备格式编码。

**教训**：仪表全绿不等于声音是对的。必须有一步直接看"设备实际输出了什么"。

### 第二个缺陷：sink 队列容不下上游水位

修完静音注入后，WASAPI 的读速率仍只有 30k/s。日志给出线索：
sink 队列容量 44 ms，而上游抖动缓冲目标是 80 ms。

于是链路变成"刚好够"：上游一填满就被 sink 一次抽到 16 ms，
之后设备大半时间在放静音，读速率自然上不去。

改成"队列容量取上游目标水位（上限为环形缓冲容量）"之后：

| 指标 | 修前 | 修后 |
|---|---|---|
| 播放读速率 | 29918 /s | **49825 /s** |
| 欠载 | — | **0** |
| 丢最旧帧 | — | **0** |
| 队列容量 | 44 ms | 80 ms |

### WASAPI 的实测值（格式缺陷修好之后）

修掉格式缺陷后，同一套端到端方法给出 **210.90 ms**（4 次中位数，
分散 192–211 ms）。此前那句"WASAPI 的数字一律不给"由此作废。

检测器也在同期改成了"先按包络定位、再局部相关细化"：
原来的全局相关在静音段会锁到搜索起点，给出 0.00 或负数。
配合"每轮重启接收器"与"只向交出时刻之后搜索"，数值才稳定下来。

### 测量方法本身修正过三次（记下来免得再犯）

1. **搜索窗口开在交出时刻之前**：相关器在静音段锁到窗口起点，
   算出 −250 ms 这种负数。信号不可能早于它被交出，改为只向后找；
   并要求相关峰明显高于起点值，否则报"未找到"而不是返回一个数。
2. **轮与轮之间不隔离**：复用同一个接收器时，发送端节拍略慢于实时，
   环里积压逐轮减少，测出的延迟逐轮变小（335 → 201 → 184 ms）。
   改为每轮重启接收器，从同一初始状态起测，数值才可比较。

**§0 验收标准 1（延迟显著降低）现在有两条独立的实测证据**：

| 手段 | 由 → 到 | 降幅 |
|---|---|---|
| 同档位缩池（16 → 4） | 339.81 → 143.08 ms | **−58 %** |
| 换后端（waveOut → WASAPI 共享） | 339.81 → 210.90 ms | **−38 %** |

两者都不是"感觉快了"，而是同一套端到端方法测出来的。
注意**池比后端更有效**：waveOut 池=4 的 143.08 ms 甚至低于 WASAPI 的 210.90 ms。

尚未验证的是**稳定性**：池=4 是否在长时间、差网络下仍然零欠载，
还没做长跑对照——在那之前不能把它当作推荐配置。

独占模式无法用 loopback 采集（绕过混音器），只能用物理回环，
这点在工具的报错里已写明，不静默。

### 写这个工具时踩的三个坑（都会伪装成"设备不行"）

1. **忘了调 `Start()`**：采集线程没启动，帧数恒为 0，
   表现为每次都报"采集样本不足"，极易误判成设备不支持 loopback。
2. **两套设备编号混用**：`EnumAudioEndpoints` 与 `waveOutGetNumDevs` 顺序不同，
   同一个数字指向不同设备，于是"送到 A、采 B"，一个包都采不到。
   按设备名映射才可靠，且映射结果要打印出来。
3. **没减去静音前缀**：噪声串放在流内 0.5 s 处，不减去就会得到 529 ms 这种假数。
